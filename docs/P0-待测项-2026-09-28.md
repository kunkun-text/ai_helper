## 一、N19 教师端越权修复（⏳ 未实测）

**改了什么**：token 值改为 `userNumber|role`；新增 `@RequireRole` 注解 + 拦截器角色校验；
`/teacher/**`、`/editUserInfo` 纳入登录保护；改资料校验「只能改自己」。

### 要验什么

| # | 步骤 | 预期结果 | 打勾 |
|---|---|---|---|
| 1 | 学生账号登录，取到 token | 登录成功，返回 `token` / `role: student` | ☐ |
| 2 | 用**学生 token** 调教师接口：`GET /teacher/defense/records` | **403** + `当前账号无权访问该功能` | ☐ |
| 3 | 用**学生 token** 调 `POST /teacher/addDefense` | **403**（不能被学生增删改课题） | ☐ |
| 4 | **不带 token** 调 `/teacher/getAllDefense` | **401** + `未登录或 token 缺失` | ☐ |
| 5 | 教师账号**重新登录**后调 `/teacher/defense/records` | 200 正常返回记录列表 | ☐ |
| 6 | 学生改自己资料：`POST /editUserInfo`，请求体 `id` = 自己 | `保存成功` | ☐ |
| 7 | 学生改他人资料：请求体 `id` = 别人的 user_id | `只能修改自己的资料` | ☐ |
| 8 | 教师端页面走一遍（课题增删改 + 记录查询 + 改资料） | 全部正常，无回归 | ☐ |

### 风险与注意

- ⚠️ **旧 token 的教师需要重新登录一次**（旧 token 里没有角色信息）→ 会提示「登录信息缺少角色，请重新登录」，属**预期行为**，不是 bug。
- 小程序侧**无需改动**（teacher.js / student.js 相关请求本就带 `Authorization` 头）。
- 拦截器只对 `WebConfig.PROTECTED_PATHS` 内的路径生效；答辩链路 `/api/chat` 不在其中，未受影响。

### 回滚方式

`Config/WebConfig.java` 的 `PROTECTED_PATHS` 去掉 `/teacher/**`、`/editUserInfo` 即恢复旧行为。

## 二、N20 写流程事务（⏳ 未实测）

**改了什么**：`saveAiQuestion` / `savePresetQuestionAnswer` / `startOrResumeDefenseRecord` / `finishDefenseRecord`
补 `@Transactional(rollbackFor = Exception.class)`；catch 由「log 后 return」改为「记上下文 + 抛 `BusinessException`」；
`DefenseTopicsServiceImpl#addDefense/editDefense` 去掉 catch-return（**原 `@Transactional` 因吞异常而失效的问题一并修掉**）。

### 要验什么

**方式 A（快，5 分钟）**——构造写库失败，看是否「要么全成、要么全不写」：

| # | 步骤 | 预期结果 | 打勾 |
|---|---|---|---|
| 1 | 加约束：`ALTER TABLE defense_answers ADD CONSTRAINT chk_rb_test CHECK (student_answer <> 'ROLLBACK_TEST');` | 执行成功 | ☐ |
| 2 | 进答辩，第 1 题故意输入 `ROLLBACK_TEST` 并发送 | 前端报错/提示失败（不再静默） | ☐ |
| 3 | 查库：`SELECT COUNT(*) FROM defense_score_record WHERE defense_id=<本次> AND round_num=1;` | **0** —— 评分行必须一起回滚（不能只落一半） | ☐ |
| 4 | 清理：`ALTER TABLE defense_answers DROP CONSTRAINT chk_rb_test;` | 执行成功 | ☐ |

**方式 B（同时验教师端）**——`addDefense` 中途失败是否整条回滚：
临时把 `defense_questions.question` 改 `NOT NULL` 无意义；更简单的做法是直接**代码审查 + 看日志**：
确认 `addDefense` / `editDefense` 里已无 `catch (...) { return Result.error(...) }`（否则事务不生效），且失败时日志只有一条 `GlobalExceptionHandler` 的 `未处理的异常`。

### 风险与注意

- **行为变化（预期内）**：写库失败从「记日志继续」变成「抛异常 + 回滚」→ 以前可能留下半截数据，现在宁可不写。
- 答辩主流程已有兜底 catch（`sendMessageWithMemory` 外层），不会把异常抛给前端；但**该轮答案会丢**（这是一致性的代价）。

## 三、N21 异步落库可观测 + 末轮同步（⏳ 未实测）

**改了什么**：`saveRoundScoreAsync` 返回 `CompletableFuture<Boolean>`（失败不再无信号）；
新增同步方法 `saveRoundScore`；**最后一轮改同步落库**（修「收尾聚合总分时末轮分数还没写库」的漏算窗口）。

### 要验什么

| # | 步骤 | 预期结果 | 打勾 |
|---|---|---|---|
| 1 | 跑一场完整 10 轮答辩（正常作答） | 第 10 轮收尾正常 | ☐ |
| 2 | 核对总结里的总分与库中的关系 | 见下 | ☐ |
| 3 | `SELECT ROUND(AVG(expression_score+logic_score+professional_score+adaptability_score+innovation_score)/5,1) AS avg_total, COUNT(*) FROM defense_score_record WHERE defense_id=<本次>;` + `SELECT score FROM defense_records WHERE defense_id=<本次>;` | **两值相等**，且 `COUNT(*)=10`（末轮分数已算进总分） | ☐ |
| 4 | 日志中搜 `保存评分成功` | 10 条，`roundNum` 1~10 各一条 | ☐ |

### 风险与注意

- 末轮多一次**同步**写库（约几毫秒），可忽略；其余轮次仍异步，不拖慢答辩。

## 四、N22 会话记忆锁（⏳ 未实测）

**改了什么**：`ChatConfiguration.RedisChatMemory.add` 去掉「取不到锁就无锁强制写」，
改为「等待 50ms × 最多 5 次重试」，仍失败则**放弃本次写入**（少一条上下文 < 污染整场会话）。

### 要验什么

| # | 步骤 | 预期结果 | 打勾 |
|---|---|---|---|
| 1 | 同一 sessionId **并发**发两个 `/api/chat` 请求（两个终端几乎同时 curl） | 两个请求都返回 | ☐ |
| 2 | `redis-cli LLEN chat:memory:user_<学号>_topic_<课题>` | 消息条数**不翻倍**（无重复写入） | ☐ |
| 3 | 日志搜 `【Redis锁】` | 正常路径无 `放弃本次会话写入`；若出现，说明确实冲突过并已按设计放弃 | ☐ |

### 风险与注意

- 极端并发下**可能少一条上下文**（设计取舍），但不会出现「同一问题被模型看到两遍」。
